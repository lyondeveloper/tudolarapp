### Observed (external, point-in-time; URLs in §8)

- OpenAI "Structured Outputs" guarantees outputs adhere to a supplied JSON Schema and makes safety refusals programmatically detectable; the schema counts toward input tokens (`developers.openai.com/api/docs/guides/structured-outputs`).
- Published list prices observed on the pricing pages (per 1M tokens): small/nano tiers roughly $0.05–$0.75 input and $0.40–$4.50 output; mid tiers ~$2–$5 input / $10–$30 output (`developers.openai.com/api/docs/pricing`; `platform.claude.com/docs/en/about-claude/pricing`; `ai.google.dev/gemini-api/docs/pricing`). **These change; re-verify at implementation time.**
- Data handling: OpenAI API data is not used for training by default and abuse-monitoring logs are retained up to 30 days unless Zero Data Retention is approved (`developers.openai.com/api/docs/guides/your-data`; `openai.com/business-data/`). Gemini's **free tier** is documented as "Used to improve our products: Yes," while the paid tier is "No" (`ai.google.dev/gemini-api/docs/pricing`) — the free tier is unsuitable for user text.
- Prompt injection is a top LLM risk; OWASP recommends constraining behavior, **validating expected output formats with deterministic code**, input/output filtering, and least privilege (`genai.owasp.org/llmrisk/llm01-prompt-injection/`; OWASP LLM Prompt Injection Prevention Cheat Sheet).
- Latency: fine-tuned 270M-class models can answer function-calling prompts in ~10–50 ms on-device, whereas cloud small models were measured around p50 ~0.5 s / p95 ~0.8 s (Gemini 2.5 Flash-Lite) and ~0.7–1.2 s (Claude Haiku 4.5) (`distillabs.ai/learn/what-latency-can-you-expect-from-an-slm/`). Larger SLMs on constrained edge hardware can take tens of seconds (`arxiv.org/html/2504.19277v1`), so on-device is only viable for a very small, specialized model.

## 3. Options considered

**A. Hosted API LLM, server-side, schema-constrained.** Provider called from a NestJS outbound adapter; the mobile client never holds the API key.
Pros: best Spanish robustness, structured-output/schema enforcement, no device constraints, observability and versioning server-side, cheapest to build. Cons: per-request cost and latency; user text leaves the device; needs network; provider availability/rate limits; DPA/retention must be configured. **Kept** as the residual path.

**B. On-device small language model (SLM).** Model bundled/streamed and run on the phone.
Pros: offline parsing, no user text leaves the device (strongest privacy), no per-request cost. Cons: app-size and memory cost, device fragmentation, accuracy on Spanish/Venezuelan slang unproven, latency highly variable on low-end hardware, model updates require app releases, and it moves parsing into the client where criteria could be forged — the backend must still validate everything. **Rejected as the primary path** for the MVP; kept as a possible offline nicety only after the deterministic fallback exists.

**C. Rules-first deterministic parser (no LLM).** Regex/dictionary/alias table for currencies, pair verbs ("cambio", "vendo", "necesito"), amount patterns, and known area aliases.
Pros: zero cost/latency/network, fully offline, auditable and testable, no privacy exposure, no injection surface. Cons: brittle on typos, word order, and slang; maintenance burden as vocabulary grows; poor on genuinely free phrasing. **Kept** as the first stage and the mandatory fallback.

**D. Hybrid: rules-first, hosted LLM for the residual (recommended).** The deterministic parser resolves the common cases; only unparsed/ambiguous text is sent to the hosted model; every result — from either path — is re-validated against the closed schema.
Pros: reduces cost, latency, and PII exposure to only the hard cases; degrades gracefully to C when offline or when the provider fails; keeps one validated criteria object feeding one search path. Cons: two code paths to test; the boundary (when to escalate) needs a rule and metrics. **Kept** as the recommendation.

**E. Self-hosted open-weight model on own infrastructure.** Pros: data residency control, no third-party dependency, cost predictable at high volume. Cons: operational burden (GPU serving, scaling, upgrades), not justified at pilot scale, contradicts "avoid microservices until traffic justifies them" (`docs/architecture.md:3`). **Rejected** for the MVP; revisit only if volume or residency demands it.

## 4. Recommendation

Adopt **Option D (rules-first with a hosted, schema-constrained LLM fallback)** behind a single port, and select the concrete provider by the scorecard below. Mark the framework/provider choice **unresolved** for product and security (§5): this spike recommends with trade-offs, it does not decide.

- **Port and placement.** Define an `IntentParserPort` (input: raw Spanish text + active-market context; output: the closed criteria object or an explicit "cannot parse"). Implement adapters under `adapters/out/` following `apps/api/src/auth/adapters/out/` and the `Unavailable`/config-selected pattern in `apps/api/src/auth/auth.module.ts` and `apps/api/src/config/env.validation.ts`. The key stays server-side; no provider secret is ever bundled in the app (`AGENTS.md:97`).
- **Schema-constrained output.** Require the provider's structured-output/JSON-schema mode so the model cannot emit free-form text, extra fields, or enums outside the catalog. The schema is owned by SP06; the enum values by SP01.
- **Same deterministic path as manual search.** The parsed criteria object is passed to the **same** search use case that manual filters use. There is no second query builder, no LLM-authored ordering. Ranking stays deterministic in PostgreSQL/PostGIS (`README.md:20`, `docs/architecture.md:52`).
- **Hard limits (non-negotiable).** The model: (1) never generates or executes SQL — it has no database access and its output is a fixed-shape object, never a query string; (2) never owns monetary rules — it extracts an *amount* as a number, never a rate, price, commission, or conversion; (3) never determines ranking — it returns filters only, never a sort or a "best" offer; (4) never chooses or switches the market — the active market comes from app/request context and the model's `location_hint` may only narrow, never expand or move (`AGENTS.md:9`, `docs/architecture.md:48`).
- **Cost (illustrative, re-verify).** At ~1,000 in / 120 out tokens per parse: a nano/Flash-Lite tier is roughly **$0.0001–$0.0002/parse** (~$10–$20 per 100k), a mini/Flash tier roughly **$0.0005/parse** (~$50 per 100k), a Sonnet-class tier roughly **$0.003/parse** (~$320 per 100k). Rules-first escalation to only the residual would cut these further. Prices are point-in-time (§2).
- **Latency.** Budget a UI target of a few hundred ms for the rules path and ~0.5–1.5 s for the hosted path, with a spinner and a manual-filter fallback on timeout. Do not block the event loop on the call (`AGENTS.md:76`); use an async outbound adapter with a hard timeout.
- **Fallback.** On timeout, provider error, rate limit, offline state, or unparseable output: silently fall back to the deterministic parser and, failing that, to manual filters (`docs/flows/search-and-contact.md:47`). Never show a raw error as a dead end.
- **Observability.** Log parse latency, chosen path (rules vs LLM), schema-validation pass/fail, escalation rate, and fallback rate — with retention/access rules and **no raw user text by default** (`AGENTS.md:75`).

### Evaluation method and scorecard

Build a **fixture set** of ≥40 realistic Ciudad Ojeda phrasings, run every candidate under identical prompts/schema, and score each fixture as *exact match*, *clarification asked*, or *rejected*. Report per-model: schema-valid rate, exact-criteria rate, clarification rate on ambiguous cases, injection-resistance, p50/p95 latency, and $/parse. The fixture categories:

| Category | Example phrasings (illustrative) | Expected behavior |
| --- | --- | --- |
| Clear, documented | "necesito 50 dólares en efectivo por Zelle en la Intercomunal" | Parse to the documented criteria shape |
| Clear, alternative order | "vendo 100 USDT, pago en efectivo, por la Intercomunal" | Same fields, order-independent |
| Slang / colloquial | "¿quién cambia verdes por bolívares cerca del centro?" | Parse, or clarify which currency is given vs received |

| Unsupported pair | a pair outside the approved ten (`backlog2.md:110`) | **Reject** / explain unsupported |

| Market-change attempt | "busca en Maracaibo" | Ignored for market scope; clarify only |

### Detecting and rejecting bad parses

The parser is an untrusted input source; nothing it returns reaches the query without passing the same deterministic gate manual input passes. Rejection is layered so a single failure cannot leak into search:

1. **Transport/shape.** Structured-output mode plus a strict schema means missing keys, extra fields, wrong types, or truncated JSON are structurally impossible or immediately detectable. A schema failure is a reject, never a repair (`developers.openai.com/api/docs/guides/structured-outputs`).
2. **Enum allowlist.** `payment_method_offered`/`payment_method_wanted`/pair direction must be members of the SP01 catalog. An unknown value is a reject, not a best-effort guess.
3. **Amount sanity.** The amount must be a positive number of the expected type and within the configured min/max; the model extracts a number and never a rate, price, commission, or conversion (`AGENTS.md:11`).
4. **Ambiguity contract.** The schema allows a field to be explicitly `null`/absent; when the model is unsure it must leave the field empty rather than guess. A missing required field, or a deliberately ambiguous fixture, routes to clarification (`docs/flows/search-and-contact.md:11`).
5. **Market containment.** The `location_hint` is resolved and checked against the active market polygon; outside it, the app asks to switch/clarify and never silently searches elsewhere (`docs/architecture.md:48`).
6. **Injection screening.** Input is normalized and screened (length caps, character-set restrictions, injection patterns) before the call, and the output is checked to contain only schema fields — no SQL, no tool calls, no free text (`genai.owasp.org/llmrisk/llm01-prompt-injection/`). Because the model cannot act, only emit criteria, injection's blast radius is bounded to a wrong filter set, which the gate above still validates.
7. **Failure budget.** Timeout, provider error, or repeated validation failure abandons the LLM path for that request; it does not retry indefinitely.

### Offline behaviour

The LLM path requires network; the product must not (`AGENTS.md:99-100`). When the device is offline, RTK Query + NetInfo report the state, the app runs the deterministic parser locally, and if that fails it presents manual filters — full search remains available with no LLM. When the provider is reachable but slow, the request is bounded by a hard timeout after which the deterministic parser takes over. No local write is ever presented as server-confirmed.

## 6. Product and technical impact

- **Product.** Natural-language search stays a convenience layer over the same results manual filters produce; the parser cannot change what is searchable, the price, the ordering, or the market. Clarification prompts (not silent guesses) on ambiguous amounts/directions and out-of-market locations protect users from wrong matches. Offline/no-network users keep full manual search.
- **Technical.** Adds one outbound port + adapters, one new provider dependency, provider config/secrets, and a parser test suite; no change to the search query, ranking, or data model. Every parser output passes strict DTO validation (schema, enums, amount bounds, market containment) before reaching the search use case — the same gate manual input passes. New E2E scenarios exercise the parser via the API contract, using fixtures rather than a live provider (`docs/testing/e2e.md`).

## 7. Testable scenarios

- **WHEN** a user submits "necesito 50 dólares en efectivo por Zelle en la Intercomunal" in the Ciudad Ojeda market, **THEN** the API returns offers whose criteria equal the documented shape (`docs/flows/search-and-contact.md:33-44`), produced by the same search use case manual filters use.
- **WHEN** the parser returns a schema-invalid object, an unknown enum, or an amount outside configured bounds, **THEN** the request is rejected before any query runs and the user is asked to refine or use manual filters.
- **WHEN** a prompt mentions an out-of-market location ("en Maracaibo"), **THEN** no out-of-market offer is returned and the user is asked to switch market or clarify; the active market is unchanged.
- **WHEN** GPS is disabled or denied, **THEN** the parse/search still runs against the whole active node and no query expands beyond it.
- **WHEN** a prompt contains an injection or SQL string ("DROP TABLE offers"), **THEN** no SQL is generated or executed, the response contains no offers outside the active market, and no system prompt or provider detail is revealed.
- **WHEN** a prompt asks for a price, rate, or ranking ("la mejor tasa"), **THEN** the response returns only filter criteria; no monetary value is computed and ordering is the deterministic default.
- **WHEN** the provider times out, errors, or the device is offline, **THEN** the request falls back to the deterministic parser, and failing that to manual filters, without a dead-end error.
- **WHEN** the fixture set is run against a candidate, **THEN** the scorecard reports schema-valid rate, exact-criteria rate, clarification rate, injection resistance, p50/p95 latency, and $/parse.
